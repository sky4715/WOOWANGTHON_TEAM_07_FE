# 랜딩 화면 선택과 메인 화면 분리

등록일: 2026-11-15 · 관련: REQ-COM-011

## 최종 사용자 요구와 구현

웹사이트 루트에 접속하면 중앙에 서비스명과 엘리베이터 심볼을 배치하고, 그 아래 ‘기본 화면으로 시작’과 ‘나에게 맞게 시작’을 보여준다. ‘어떤 화면으로 이용하시겠어요’ 질문은 제거했다. 별도 로고 이미지 파일은 저장소에 없어 기존 서비스명과 코드로 그린 SVG 심볼로 구성했다. 기본은 노선도로 바로 들어가고, 맞춤은 이전에 제공한 접근성 옵션을 직접 선택한 뒤 메인으로 들어간다. 메인 상단 맞춤 설정 배너는 노출하지 않는다.

| 주소 | 화면 | 역할 |
|---|---|---|
| `#/` 또는 루트 | 랜딩 | 두 화면 중 하나 선택 |
| `#/customize` | 사용자 맞춤 설정 | 글자 크기·대비·큰 버튼·움직임 감소·간단한 첫 화면·계단 이용 도움을 조합 |
| `#/easy` | 쉬운 메인 | 큰 기능 버튼으로 주요 과업 선택 |
| `#/main` | 기본 메인 | 기존 지하철 노선도와 탭 |
| `#/easy/elevator` 등 | 쉬운 화면의 기능 | 실제 기능 이용, 쉬운 홈으로 돌아가는 일반 탐색 링크 |

루트 접속은 저장 설정이 있어도 랜딩을 보여준다. 선택 후 메인 주소 새로고침은 해당 메인을 유지한다. 브라우저 뒤로 가기로 랜딩으로 돌아올 수 있다. 쉬운 메인은 별도의 배경·헤더·제목·과업 영역을 사용하며 랜딩 소개와 선택 버튼을 함께 노출하지 않는다.

맞춤 설정은 저장한 선택을 불러오며 처음에는 큰 글씨(lg)·큰 버튼·움직임 감소·간단한 첫 화면을 제안한다. 글자 4단계와 도움 옵션을 각각 바꿀 수 있고 바로 미리 적용한다. 간단한 첫 화면이나 계단 이용 도움을 고르면 기능 버튼 메인으로, 그 외에는 맞춘 크기·대비가 적용된 노선도로 연결한다. 설정은 메인 진입·기능 이동·새로고침 이후에도 유지한다. 기본 화면은 기본 글씨와 기존 버튼 크기로 시작한다. 두 방식 모두 로그인은 필요 없다.

## 사용자별 검토

아래는 설계 가설이며 참여자 조사를 완료했다는 의미가 아니다. [W3C 고령 사용자 자료](https://www.w3.org/WAI/older-users/), [고령 사용자를 위한 설계 설명](https://www.w3.org/WAI/older-users/developing/), [표적 크기 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)을 참고했다.

| 사용자 상황 | 고려한 불편 | 반영·남은 검증 |
|---|---|---|
| 어르신·디지털 사용이 낯선 사람 | 복잡한 초기 설정과 지도 탐색 | 첫 선택을 두 가지로 단순화, 쉬운 메인에서 기능을 큰 버튼으로 제공. 실제 이해도 조사 필요 |
| 저시력 | 작은 글씨와 좁은 표적 | 쉬운 화면의 글씨·터치 확대. 화면 확대기와 200% 이상 확대 별도 검증 필요 |
| 색 구별의 어려움 | 색만으로 구분하는 상태 | 기존 상태 문구·아이콘 유지. 노선의 색각 시뮬레이션 필요 |
| 손 떨림·운동 기능 어려움 | 작은 버튼·복잡한 절차 | 큰 화면 선택 버튼, 쉬운 모드의 56px 기준. 지도 SVG·작은 보조 조작 전체 감사 필요 |
| 인지·주의·기억의 어려움 | 설문과 중간 단계로 인한 부담 | 선택 한 번으로 진입, 쉬운 메인에서 과업 네 가지 제공 |
| 청각 관련 불편 | 소리에 의존하는 안내 | 시작과 기능 안내를 모두 글로 제공 |
| 화면낭독기 이용 | 화면 구분과 초점 위치 | 실제 button·제목·nav·link, 화면 전환 시 초점 이동. NVDA·VoiceOver 실기 검증 필요 |
| 휠체어·유모차·계단 이용 어려움 | 설비 고장·단절된 경로 | 엘리베이터 확인을 쉬운 메인의 첫 과업으로 제공. 전체 경로 접근성을 보장하지 않는 안내 유지 |
| 움직임에 민감한 사람 | 반복 애니메이션 | 쉬운 화면에서 CSS 움직임 감소, OS reduced-motion 반영. 자바스크립트 모션 별도 평가 필요 |
| 저속 통신·저사양·비공개 모드 | 외부 자원 실패·저장 차단 | 이미지 다운로드 없는 랜딩, 외부 폰트 실패 시 대체, 저장이 막혀도 화면 진입 가능 |

56px은 프로젝트의 사용 편의를 위한 기준이며 WCAG AA의 최소 요구값이라고 표현하지 않는다. 실제 접근성 인증·현장 경로 검증을 수행했다고 주장하지 않는다.

## 저장과 사용자 취합

선택한 모드는 기존 브라우저 Preferences 저장 형식에 기록한다. 저장값으로 루트 랜딩을 자동 생략하지 않는다. 연령·장애명·개인별 조사 데이터는 수집하지 않는다. 서버의 사용자 모집·통계·계정별 동기화는 구현 범위에 포함하지 않는다.

## 검증

- TypeScript 검사·Vite 빌드 통과.
- 랜딩·맞춤 설정 관련 4개와 기존 AppShell 13개, 총 17개 테스트 통과.
- `node scripts/verify-welcome.mjs`: Chromium에서 로고와 두 선택 버튼, 320/375/768/1440px 가로 넘침, 375×667px 첫 화면의 두 버튼 노출, 기본 진입·맞춤 설정 조합·저장·새로고침 복원, 기능 연결, 뒤로 가기, 루트 재접속을 검증했다.
- 화면 이미지는 `web/artifacts/welcome/`의 `landing-desktop.png`, `landing-mobile.png`, `easy-main-mobile.png`, `basic-main-mobile.png` (Git 제외).
- 기존 `test:browser`·`test:visual`은 루트에서 바로 노선도를 전제하므로 이번 결과로 인용하지 않는다. 재실행 시 기본 메인 주소를 사용하도록 준비해야 한다.
- 실제 참여자 평가·화면낭독기·Safari/iOS·현장 이동·서버 통계는 검증하지 않았다.

후속 사용자 평가는 ‘두 화면의 차이 이해 → 화면 선택 → 설비 찾기 → 출발 시각 확인’을 중심으로 성공 여부·오조작·도움 요청·피로도를 요구별로 비교한다.
